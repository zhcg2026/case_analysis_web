## 1. PyTorch wheel：根路径缺失，缓存中有候选

历史 Dockerfile 从项目根目录 COPY：

`torch-2.13.0+cpu-cp311-cp311-manylinux_2_28_x86_64.whl`

根目录没有该文件，故按现有输入无法完成这条 COPY。`pip_cache/` 中存在同名候选，本次只读核验如下：

| 项 | 核验结果 |
|---|---|
| 文件大小 | 191,794,682 字节 |
| SHA256 | `6746dbcbeb526eb61330b76b41ff1b4eb848951103a892eeb080dfa2b264667b` |
| 分发名 / 元数据版本 | `torch` / `2.13.0+cpu` |
| Wheel 标签 | `cp311-cp311-manylinux_2_28_x86_64` |
| 压缩包 CRC | 所有成员通过 |
| 是否安装、执行或移动 | 否 |

观测的运行平台是 Linux/amd64、Python 3.11.15，torch 分发版本记录为 `2.13.0`。候选标签与目标平台方向一致，但 CPU 变体等价性、动态库兼容性、依赖解析和上游来源哈希未验证。CRC 和上述 SHA256 只能证明该缓存文件可完整读取并标识当前字节，不证明它就是现网实际使用的同一构建。

后续需先确认使用哪一个经过验证的二进制材料，再决定补齐根目录输入还是调整 COPY 路径。不要仅把缓存挪到根目录就宣称可复现；本次没有改 Dockerfile 或移动文件。Wheel 是单独保管的二进制材料，不提交 GitHub。

## 2. Python、系统包与前端输入

- 观测的 110 个 Python 发行包中，`requirements.txt` 声明的 25 个直接依赖均存在且满足版本范围。
- 这些直接声明主要使用 `>=`，不固定传递依赖，也未指定安装材料哈希；满足下限不能证明下次解析仍得到同一环境。逐项声明/观测版本已放在 JSON 的 `direct_requirements` 中，避免把它冒充生效安装文件。

本次没有把观测版本直接覆盖 `requirements.txt`，没有生成可被误当作已验证锁定安装方案的文件。

## 3. 构建上下文仍需数据隔离审查

历史 Dockerfile 会 COPY backend 子树；旧 `.dockerignore` 未显式列出 uploads、backups、reports、monthly_report/work、qa 和 pip_cache 等目录的排除项。构建前应审查敏感/业务文件及缓存边界，避免不必要的数据进入上下文或镜像。

JSON 只记录“是否有显式排除行”，不是完整 Docker ignore 规则模拟器；本次未把任何业务文件打包给构建器，也没有修改忽略规则。此项需另行设计并确认不会排除运行必需输入后，再更新真实规则。
