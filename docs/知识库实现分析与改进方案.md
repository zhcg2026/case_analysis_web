# 知识库实现分析与改进方案

> 修订（2026-07-24）：按用户明确约束修订——① **真统一**：只用一个 Milvus 集合，不再"两套集合 + 查询时缝合"；② **不用同义词方案**：问题千奇百怪，同义词匹配不上就反馈"知识库中暂无相关"，不可接受。

---

## 一、当前实现逻辑（探索结论）

### 整体架构
项目里围绕"知识库"实际是 **两个独立 Milvus 向量库 + 一个查询时手工缝合的"假统一层"**：

1. **通用知识库 `rag.py`** — 集合 `knowledge_base`
   - 文档（txt/md/docx）按 `\n\n+` 切段，聚合到 1500 字/块，overlap 100。
   - 向量：服务端 Ollama `jina-embeddings-v2-base-zh`，本地 `paraphrase-multilingual-MiniLM-L12-v2`。
   - 检索：向量(COSINE) + jieba/BM25 关键词，权重 0.7/0.3。
2. **立结案标准库 `case_standards.py`** — 集合 `case_standards`
   - 解析"立案结案标准"txt，拆成 parent(level0)/child(level1) 两层扁平存同一 collection。
   - 检索：向量 + 同义词滑窗扩展(`case_type like`) + 关键词/核心词/意图字段加权 → `final_score`。
   - 附带一整套地理派单逻辑（点面/点线判定归属部门）。
3. **"统一"入口 `kb_unified.py`** — `unified_ask` / `unified_search`
   - 查询时分别调 `rag.search_similar` 和 `search_case_standards`，再把两套**量纲不同**的分数用手工公式归一化后合并排序，最后拼 context 给 LLM。

辅助：`kb_common.py`（配置/embedding/LLM 调用）、`kb_synonyms.py`（同义词表）、`knowledge_routes.py`+`kb_routes.py`+`case_standards_routes.py`（三套路由）。

### 数据流
上传 → chunk → embed → 写 Milvus → 前端 `/api/knowledge|kb|case-standards/*`
问答 → 查询 → 双库检索 → 合并/重排 → LLM 生成 → 返答案+来源

### 当前数据与环境现状（落地前置，必须正视）
> 上面分析的是"代码逻辑"，但**当前知识库里没有数据**——这是动手前最该认清的现实。

- **本地库从未建立**：本地模式(`USE_LOCAL_MODE=true`)用 Milvus Lite 文件 `./local_milvus.db`，但该文件在整个项目中**不存在** → 本地库一次都没建过、没索引过任何数据。
- **Docker Milvus 未运行**：本机 `docker ps` 无 milvus 容器在跑，亦无可用生产库。
- **代码不自启动索引**：`app.py` 启动不会自动索引；数据仅在手动调 `/api/knowledge/init` 或 `/api/case-standards/index` 时才写入，默认即空库。
- **原料在、没入库**：源目录 `D:/常用/立案结案标准` 含 **237 个 .txt 立结案标准文件**（交通设施/市容环境/绿化/施工管理等），但**从未被索引进 Milvus**。
- **环境依赖未装**：本机无 `.venv`，`pymilvus`/`sentence-transformers`/`jieba` 等均未安装 → 当前连"索引"这个动作都跑不起来。

**含义**：检索/同义词那套 redesign 解决的是"有数据但找不准"；而眼下第一道坎是"**有原料、没入库**"。因此阶段0 的实际第一步是 **建环境 + 写统一索引脚本把 237 个文件真正灌进单集合**，而不是"迁移旧数据"（旧数据本就为空）。

## 二、主要问题（按严重程度）

### P0 实质缺陷
1. **"统一知识库"是假的（`kb_unified.py` + `migrate_general_to_unified`）**：没有真正的统一集合，`unified_ask` 只是查询时 fan-out 到两个独立集合；`migrate_general_to_unified` 把通用库从 `knowledge_base` 读出来又**写回同一个 `knowledge_base`**（doc_id 加 `migrated_` 前缀），等于自我复制，无任何"统一"。命名误导且污染统计。
2. **同义词/关键词门控导致"暂无相关"（覆盖率根因）**：`case_standards.py:1073-1111` 对查询做 2-4 字暴力滑窗，每词查 `SYNONYM_MAP` 再 `case_type like "%syn%"`。用户换了种说法、片段不在词表里 → 扩不出同义词 → `like` 命中为空 → 被判"不相关" → 返回"知识库中暂无相关"。**问题千奇百怪，人工词表永远补全不了，这是产品级缺陷。**
3. **BM25 用法错误（`rag.py:262-294`）**：对每个候选文档单独 `BM25Okapi([doc_tokens])`（语料只有 1 篇）再 `get_scores[0]`。BM25 必须在**整个文档集合**上 fit 一个语料库才有意义；当前 IDF 退化为常数，等于"查询词在单篇里的词频"，既不对又和前面 `like` 匹配重复。
4. **合并排序无原则（`kb_unified.py:177-189`）**：标准库分 `(score-0.2)/0.6` 再 `+0.05`，通用库直接取 cosine。两个分布不同的分硬加排序，结果不可信，magic number 无依据。

### P1 设计/安全风险
5. **两套 schema 割裂**：rag 用 `content/source/metadata`，标准库用 `text_content/case_type/meta_info(level)`，字段/embedding 调用/搜索函数全双份，维护成本翻倍。
6. **Embedding 维度隐患**：rag 默认 `dim=768` 写死，标准库用 `get_embedding_dim()` 动态取。若模型维度不一致，迁移/混用会直接报错（统一到单集合后此问题自然消失）。
7. **硬编码密钥与路径**：`kb_common.py:29` 明文 `DOUBAO_API_KEY`；`case_standards_routes.py:53,138` 硬编码 `D:/常用/立案结案标准`。
8. **无重排序（rerank）**：向量召回 top_k 直接进 context，短查询+长文档时召回精度差；context 截断 500 字丢信息。
9. **无引用溯源**：LLM 返纯文本，sources 仅是 case_type 列表，用户无法定位原文、无法核验，违背"反幻觉"诉求。

### P2 工程化
10. 模块级全局 `_milvus_connected/_milvus_client` 非线程安全；embedding/LLM 全同步阻塞，无缓存。
11. 大量 `print` 无 logging；无检索延时/命中率可观测性。

## 三、更好的实现（按用户约束修订）

### 用户明确约束
- **真统一**：只保留一个 Milvus 集合，不再有两套集合 + 查询时缝合。
- **弃用同义词**：删除 `kb_synonyms.py` 在召回中的使用；检索不依赖"关键词/同义词命中"作为召回门槛，避免"匹配不上就暂无相关"。

### 为什么能丢掉同义词
"暂无相关"的根因**不是知识库没内容，而是召回被关键词/同义词门控卡死**。语义向量检索天生能处理同义改写——"路灯不亮""照明设施坏了""灯杆灭了"在向量空间里很近，不需要人工词表。所以正确做法是**以语义检索为唯一召回主路径**，同义词这种 brittle 规则整体移除。这正好满足"问题千奇百怪也不该误判暂无"的要求。

### 目标架构（单集合 + 语义优先）
```
 ingest ─► 统一解析/分块 ─► dense embed ─► 单一 Milvus 集合(doc_type 区分)
                                                        │
 query ─► (可选:查询改写) ─► dense 语义召回(top-N) ──┐
                                              (可选 sparse 兜底,见下) │
                                                        ▼
                                                 取 top-K / RRF 融合
                                                        │
                                                  (可选 rerank)
                                                        │
                                              LLM(强约束 + 引用JSON)
                                                        │
                                              答案 + citations(可点击溯源)
```

### 关键改动
1. **单一集合 + 统一 schema**：一个集合（Milvus / Milvus Lite 均可），字段
   `id, doc_id, chunk_id, text, doc_type('general'|'standard'), source, metadata(JSON), embedding(FLOAT_VECTOR)`。
   立结案标准的"责任主体/监管主体/时限"等作为 `metadata` 结构化字段，可用 Milvus `expr` 精确过滤（如按 case_type 过滤），**不再靠同义词 `like` 扫**。每条立结案标准**整条作为一个 chunk 入库，不拆分父子节点**——样本实测单条标准最长仅 ~6KB，整条语义完整、向量足够准，拆分父子反而打碎上下文、增大噪声。维度统一为单一 embedding 模型，杜绝原 768/动态 的不一致。
2. **检索只走语义**：查询 embedding → COSINE 召回 top-N（如 20）→ 取 top-K（如 6）进 LLM。**删除 `expand_query`/`SYNONYM_MAP` 参与召回的全部逻辑，删除 BM25 错用**。召回不再有任何"关键词必须命中"的硬门槛，从根本上消除"暂无相关"的误判。
3. **（可选，非必须）sparse 兜底**：若担心专名/编号类精确召回（如具体案卷号、标准文号），可引入 `bge-m3` 一次出 dense+sparse，Milvus 原生 hybrid + RRF。这是**模型能力**而非人工同义词表，符合"不想维护同义词"的诉求。**不引入也完全可用，先上 dense 即可。**
4. **（可选）rerank**：召回 top-20 → 本地 `bge-reranker-base-zh` → top-6，提升精度。知识库规模不大时可先不接。
5. **引用溯源**：LLM 返回 JSON `{answer, citations:[{chunk_id, excerpt}]}`；前端按 chunk_id 定位原文。结构化强意图（时限/责任部门）可从 `metadata` 直接拼装，不必每次过 LLM。
6. **安全/配置**：密钥与索引目录走 env；`print` 换 `logging`。

### 改造还是推倒重来（策略取舍）
**结论：半推半改——检索/索引层推倒重写，地理派单业务内核保留平移。** 不是在非此即彼里二选一。

- **为什么不"纯改造"（在旧代码上打补丁）**：旧检索层是纯技术债——假统一层 `kb_unified`、错用的 BM25、`kb_synonyms` 滑窗、`rag`/`case_standards` 双份 schema、magic number 合并排序。在烂地基上修，每动一处都牵三套路由，收益低、风险高。目标架构已清晰，重写更干净。
- **为什么不"全推倒"**：`case_standards.py` 里有一套**独立的地理派单逻辑**（约 466–805 行：`_is_dispatch_question`/`_classify_department`/`_load_department_geojson`/`_point_in_polygon`/`_point_near_line_m`/`match_department_dispatch` 等），根据坐标做点面/点线判定归属部门。这是业务核心资产，且与检索**解耦**（在召回标准之后、LLM 之前执行）。重写它风险高、无收益，应整体平移。

**具体边界**
| 部分 | 处置 | 说明 |
|---|---|---|
| 检索/问答骨架 | **重写** | 新建 `kb_store.py`：单集合 ingest + 语义检索 + 引用 JSON；取代 `rag.py` 检索段 + `case_standards.py` 检索段 + `kb_unified.py` |
| 索引 ingest | **重写** | 统一切块/embed 进单集合；复用原有文件解析（txt/docx）与标准字段解析（责任主体/时限/法律依据） |
| 地理派单逻辑 | **保留平移** | 从 `case_standards.py` 抽出为独立模块 `kb_dispatch.py`，召回标准后调用做归属判定 |
| `kb_unified.py` / `migrate_*` | **删除** | 假统一层，无存在价值 |
| `kb_synonyms.py`（召回用途） | **删除** | 同义词不再参与召回 |
| `rag.py` 的 BM25 段 | **删除** | 用法错误，且语义检索已覆盖 |

一句话：**动"检索骨架"，保"业务派单"。**

### 是否还用 Milvus
**就用 Milvus**（用户已定）。单集合统一 embedding 后，原维度不一致隐患自然消失；Milvus Lite 对千级规模足够。

### embedding 模型：本地与服务器均已定（统一用 MiniLM）

> **先澄清概念**：embedding 模型 ≠ 生成式大模型（LLM）。用户说"本地没部署大模型"指的是问答用的 LLM（qwen2.5:7b / 豆包）；知识库还需要一个**轻量 embedding 模型**把文本变向量，它 470MB、CPU 能跑，**不是"大模型"**，无需部署大模型服务。

**统一单集合要求所有数据用同一个 embedding 模型（同一向量空间）**，但"用哪个"在本地早已确定：

- **本地开发（`USE_LOCAL_MODE=true`）**：原项目 `kb_common.py:27` 默认 embedding 即 `paraphrase-multilingual-MiniLM-L12-v2`（sentence-transformers 本地小模型，768 维）。**这不是待决项，本地默认就是它，且不依赖任何大模型/Ollama。** 只需 `pip install sentence-transformers` + 首次联网下载一次模型（约 470MB）。
- **阶段2 若上 sparse 兜底**：再切 `bge-m3`（1024 维，一次出 dense+sparse）。属可选升级，不阻塞阶段0。
- **服务端 Ollama `jina-embeddings-v2-base-zh`**：原代码在非本地模式下已接（`kb_common.py:22`），但需 Ollama 常驻——见下方"服务器端部署形态"。

**服务器端部署形态已定**（服务器已部署 Qwen2.5-7B 且可出外网）：本地与服务器 embedding **统一用 MiniLM**；服务器 LLM 走 `LLM_PROVIDER=ollama`（`OLLAMA_MODEL=qwen2.5:7b`），Ollama **仅做 LLM、不替代 MiniLM 做 embedding**（否则向量空间分裂、库不互通）。详见第五节"部署形态"段。

### 落地顺序（先统一，再提质）
