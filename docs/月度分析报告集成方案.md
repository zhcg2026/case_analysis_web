## 三、必须解决的两个缺口（关键前提）

### 缺口 1：`is_overtime` 字段本地不同步（服务端已有）⚠️
这是用户定的**口径铁律**（超时按 `is_overtime` 字段走，不能用处置截止时间反推）。
**2026-09-06 更正**：**服务端（生产 MySQL `case_data`）已存在 `is_overtime` 列**，是数据真源；不一致的是**本地这套 `case_analysis_web` 代码/库没同步上**：
- 本地 `analysis_routes.py` 的 `CREATE_TABLE_SQL` **没有** `is_overtime` 列，只有 `is_delayed` / `is_rework`；
- 本地 `COLUMN_MAP` 也没映射 `is_overtime` → 若本地按 `CREATE_TABLE_SQL` 建表或走上传流程，`is_overtime` 会被丢掉；
- 8 月原始 xlsx 里**有** `is_overtime` 列，但本地上传时被丢弃（服务端若从同口径导入则已保留）。
→ **不要去服务端重复加列、也不要盲目重导历史数据**（服务端已有且已填）。正确动作：
1. `analyze.py` 的 `load_from_db` 直接 `SELECT ... is_overtime ...` 从服务端读——服务端有即可用；
2. 同步本地：把 `CREATE_TABLE_SQL` 补上 `is_overtime` 列、`COLUMN_MAP` 补上映射，使本地建表/上传与服端一致（避免本地重跑时丢字段）；
3. **先核实本地库是否已有该列**：若本地 `case_data` 缺 `is_overtime`，从服务端同步表结构/数据，而非重导 xlsx；
4. 验证：对 `202608` 批次跑报告，`超时=216` 应与原 skill 8 月结果一致，证明读到的是服务端真值。

### 缺口 2：ECharts 走公网 CDN，存在白屏风险（按网络实际调整）
skill 模板头部 `<script src="https://cdn.jsdelivr.net/npm/echarts@5.5.0/dist/echarts.min.js">`，从公网 CDN 加载画图库。
**网络实际情况（用户 2026-09-06 更正）**：内部服务器具备出网能力（可访问外网），服务器本身不对组织外部暴露（内网/政务专网服务器）。
→ 因此"服务器能否拉到 CDN"不是问题；风险点转移到**查看报告的浏览器端**：
- 若客户端工作站也走公网出口，CDN 理论上能加载；
- 但政务内网常见情况是**工作站与服务器网段隔离**、工作站无公网出口，此时 iframe 内报告加载 CDN 会失败、图表全白。
> 结论：**仍建议本地化 echarts**，把风险一次性消除——前端 node_modules 已有 echarts，复制一份到静态目录零成本，且避免对外部 CDN 可用性的隐性依赖（CDN 抖动/被墙都会让生产环境白屏）。若你确认客户端工作站均能稳定访问公网，可不本地化、保留 CDN 引用，但本地化是更稳妥的默认项。

## 四、后端改动清单（待实施）

### 4.1 数据层同步 `is_overtime`（⚠️ 产线已有，仅本地对齐）
**前提**：服务端（生产 MySQL）`case_data` **已存在** `is_overtime` 列并已填充，是数据真源，**不要在产线执行任何 ALTER / 重导**。
本步只为解决"本地 `case_analysis_web` 代码与库不同步"的问题，使本地开发/跑报告时字段不丢：

文件：`backend/analysis_routes.py`
- `COLUMN_MAP` 增加：`'is_overtime': 'is_overtime'`（让上传/读取流程认识该列）
- `CREATE_TABLE_SQL` 增加列（仅本地重建表时用，幂等写法）：`is_overtime TINYINT DEFAULT 0 COMMENT '超时案件（平台认定）'`
- `process_excel_upload()` 中 `is_delayed`/`is_rework` 已用 `_normalize_bool()` 归一化，对 `is_overtime` 同样处理即可（是/否/1/0/true → 1）。

本地库对齐（仅当本地 `case_data` 缺该列时执行，**绝不在产线跑**）：
```sql
-- 仅本地开发库；产线已有，跳过
ALTER TABLE case_data ADD COLUMN IF NOT EXISTS is_overtime TINYINT DEFAULT 0;
-- 并从产线同步 202608 批次数据到本地（而非重导 xlsx），保持 is_overtime 为真值
```
> 若本地库本就无 202608 全量数据，优先**从产线 `SELECT ... WHERE upload_batch='202608'` 导出导入本地**，不要重新 `POST /api/analysis/upload` 重导（重导会先 `DELETE` 同批次，且旧上传逻辑若未含 `is_overtime` 映射会再次丢字段）。

### 4.2 新增模块 `backend/monthly_report/`
把 skill 的脚本整体搬入，只改"输入层"和"ECharts 引用"两处：

| 文件 | 处理 |
|---|---|
| `analyze.py` | 新增 `load_from_db(engine, batch)`：`pd.read_sql("SELECT * FROM case_data WHERE upload_batch=:b", conn, params={'b':batch})` → 把英文列 rename 回中文（复用 skill 的 `COLUMN_MAP` 反向映射）→ 调原 `analyze(df, cfg)`。**原函数签名不动**，仅加一个数据入口 |
| `template.html` | 改 `<script src="...cdn...">` → `<script src="/reports/echarts.min.js">`（本地化，见第六节） |
| `build_html.py` / `make_word.py` / `std_parse.py` / `polish_charts.py` / `polish_docx.py` | 原样搬入，无需改逻辑 |
| `monthly_report_routes.py` | 新增路由（见下） |
| `config.json`（模块内） | 内置默认值：org、lat、recur_radius_m=50、min_cases_supervisor=100、unit_addr_keywords、work_windows；`anomalies` 由前端传入 |

新增路由（`monthly_report_routes.py`）：
```python
# 生成 HTML 报告（写到 backend/reports/<batch>.html）+ analysis.json
POST /api/monthly-report/generate
body: { "batch": "202608", "month_cn": "2026年8月",
        "month_label": "8月份", "month_short": "8月",
        "anomalies": [{"date":"2026-08-04","type":"降雨","note":"..."}, ...] }

# 导出 Word（返回 docx 下载，Content-Disposition 带文件名）
GET /api/monthly-report/<batch>/export
```

### 4.3 注册路由
文件：`backend/app.py`

```python
from backend.monthly_report.monthly_report_routes import register_monthly_report_routes
register_monthly_report_routes(app, engine, protected)
```

## 九、风险与回滚

- **改表结构**：`is_overtime` 产线**已存在、不要动**；仅本地开发库可能需 `ADD COLUMN IF NOT EXISTS`（可 `DROP COLUMN` 回滚）。**绝不在产线执行 ALTER 或重导**，产线数据已是真值，只需从产线同步到本地。
- **新增模块独立**：`monthly_report/` 与现有 `analysis_routes.py` 互不干扰，移除只需注释注册行 + 删目录，不影响 AI 即席分析。
- **ECharts 版本**：本地用 v6，skill 模板仅用基础 setOption/line/bar/pie/scatter，无 v5→v6 破坏性差异；若个别图表异常，临时改模板引 v5 本地副本即可。
